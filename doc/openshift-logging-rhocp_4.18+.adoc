# Application Logging on Red Hat OpenShift Container Platform (RHOCP) with Loki, Vector, and the RHOCP Cluster Observability Operator

The following guide has been tested and is supported with Red Hat OpenShift Container Platform (RHOCP) version 4.22, 4.21, 4.20, 4.19, and 4.18.

Pod processes running in Kubernetes frequently produce logs. To effectively manage this log data and ensure no loss of log data occurs when a pod terminates, a log aggregation tool should be deployed on the Kubernetes cluster. Log aggregation tools help users persist, search, and visualize the log data that is gathered from the pods across the cluster. Logging 6.0 manages log storage, collection, and visualization using Loki, Vector, and the Cluster Observability's new Logging UI Plugin. After a successful installation, the Loki and log collector pods should reside inside the *openshift-logging* namespace of the cluster. Check out this link:https://docs.redhat.com/en/documentation/red_hat_openshift_logging/6.0/html/upgrading_logging/upgrading-to-logging-6#changes-in-logging-6_upgrading-to-logging-6[doc] for more information on the new changes introduced in Logging 6.0.

link:https://docs.redhat.com/en/documentation/red_hat_openshift_logging/6.6[Red Hat OpenShift Logging 6.6] is currently the latest version offered by RedHat. It follows a different versioning number system than the Red Hat OpenShift Container Platform.

## Creating a LokiStack instance

In Ecosystem > Installed Operators > LokiStack, create a new LokiStack instance. An example of a YAML file is below:
[source, yaml]
----
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.extra-small
  storage:
    schemas:
    - effectiveDate: '2024-10-01'
      version: v13
    secret:
      name: logging-loki-odf
      type: s3
  storageClassName: ocs-storagecluster-ceph-rbd
  tenants:
    mode: openshift-logging
----

### Parsing JSON logs

By default, if container logs are being output in JSON format, they will be nested inside the Vector JSON document's message field. To solve this problem, add the following YAML to the ClusterLogForwarder CR you created earlier:

[source,yaml]
----
 kind: ClusterLogForwarder
 spec:
   ...
   filters:
    - name: parse-json
      type: parse
   ...
   pipelines:
   - name: infra-app-logs
     ...
     filterRefs:
     - parse-json
----
The addition of the JSON filter above will copy the nested JSON container log into a separate `structured` field inside the Vector JSON document, where the individual fields from the JSON container log can be accessed as `structured. <field_name>`.

## Visualizing your logs using the Cluster Observability Operator's Logging UI Plugin

. Add the label `logFormat: liberty` to your OpenLibertyApplication Custom Resource. We will use this label to filter for your application pod logs in Observe > Logs.
+
[source,yaml]
----
kind: OpenLibertyApplication
apiVersion: v1
metadata:
  name: <your-liberty-app>
  labels:
    logFormat: liberty
....
----

. In your OCP web console, go to Observe > Logs to see your application logs.
+
image::images/app-logging-ocp-ui-plugin-4.18.png[See logs in OCP UI plugin]

. Use the following LogQL query to filter for and format your application pod logs.
+
[source, text]
----
{ log_type="application" } | json | structured_type="liberty_message" | line_format "[{{.structured_loglevel}}] {{.structured_message}}"
----
image::images/app-logging-ocp-LogQL-4.18.png[Query logs using LogQL]

. To see additional `structured.*` formatted individual fields from your application pod log, expand a log entry.
+
image::images/app-logging-ocp-ui-plugin-expand-4.18.png[Expand log entry]
